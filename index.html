What I bring

The same three things show up in every system I have built, whatever the domain.

Architecture that grows

A stable core behind abstractions, with features as plugins and decoupled libraries. New capability is added without editing code that is already in service.

Testing without the real thing

When the real system is slow or costly to test on, I build a simulator first, so the team can test every day at a desk.

Delivery from end to end

Requirements, design, implementation, automated tests, release pipelines and production support. Development and production built from one source.

How I start a project

The order matters: the core is the hardest thing to change later, and the tests are what let others change everything else safely.

  1. Core libraries firstThe plugin framework, networking, a thread pool, configuration and logging.
  2. Tests, then coverageUnit testing from the beginning, with coverage figures that are honest.
  3. One rule for additionsAnything added works through an abstraction that lives in its own library.
  4. A way to test it allA simulator or playback tool, so progress never waits for hardware.

Satellite communications

A plugin framework for core network software

Problem
One code base had to serve both satellite and ground, features kept arriving, and changing code already in service is a risk.
What I built
A C++ framework in which the core knows no feature. Each feature is a separately loaded module working through abstractions, with a shared thread pool and interchangeable database back ends. Designed and built with a colleague; I have led its development since.
Result
Features are added by several engineers without changes to the core.
